## Question

A rule and the reasons for it were written in one place, `spec/`, so every rule grew its history
and every reader paid for it. Where do the reasons go, so that a rule stays short and what was
weighed can still be read, by a person or an agent, years on?

## Options

| Where the reasons go               | Against it                                               |
| ---------------------------------- | -------------------------------------------------------- |
| Beside the rule in `spec/`, as now | The rule a reader needs is buried in what led to it      |
| On the design system's own pages   | Mixes what is with what was; only covers the design      |
| A file of their own per decision   | One more place, kept in form by a check rather than care |

## Decision

A file of their own per decision.

- **A rule says what is done now; an RFC says why.** The rule lives in `spec/`, or on the design
  system's page for what the design system draws. Taking the reasons already in `spec/` out of it
  is waiting work, not part of this.
- **One file, `rfcs/{scope}/{yyyy}-{mmdd}-{nn}-{slug}-{id}.md`**: the day it was written, its
  place in that day, a slug for people, and five of `[a-z0-9]` for machines. **The id is the only
  identity.** The scope is an area `rfcs/scopes.yaml` lists, named for what it is about and never
  for a repository; an area is renamed or split by moving files. It is read at
  `/rfcs/{scope}/{slug}-{id}`, looked up by the id, and a stale scope or slug redirects.
  `rfcs/` is plural as `/rfcs` is: a collection, which `data/`'s singular folders are not.
- **Nobody picks a number.** `mise run new-rfc <scope> <slug>` draws the id and the day's next
  place and writes the skeleton; `check-rfc`, which `verify` runs on every change, holds the rest.
- **It is written once the decision has landed and been pushed**, when the talk moves on, never
  while values are still being tried. It is not edited afterwards: a later RFC `supersedes` it by
  id, and that it was superseded is read off the later one.
- **Frontmatter**: `title`, the decision as a sentence; `supersedes`, ids; `commits`, `repo@hash`
  where the decision landed before the RFC was written; `references`, required, `[]` when the idea
  is our own, each with the origin's `url`, what it `took`, and `via` where it was found when that
  is not the origin.
- **An RFC names nothing that moves.** Another RFC is named by its id alone, never by its area or
  its slug, and no page or spec is named in its frontmatter, so renaming either costs nothing here.
  A link runs the other way: a rule cites the RFC behind it by id, `RFC 2ut6h`, and which rules an
  RFC settled is read off the citations.
- **Body**: `## Question` and `## Decision`, required; `## Options`, the values in the order they
  were tried, and `## Evidence`, only where they can still be traced; in that order. Short and
  not thin: a table or a specimen before a paragraph.
- **No source is named in the body.** `references` carries them, listed beneath the RFC they
  belong to and nowhere else.
- **A specimen is called, never drawn inline**, in the corpus's directive syntax (`::`, `:::`,
  `:`) and with its values written in it, so the raw file still reads; only components space
  registers can be called, and a new kind of comparison is made there first.
- **Everything here is published, so no example is somebody's.** A host or a mail address outside
  `references` is one RFC 2606 reserves -- `example.com`, `.net` or `.org`, or a name under
  `.example`, `.test`, `.invalid` or `localhost`, at any depth -- and an IP address is from RFC
  5737's documentation ranges; `check-rfc` refuses any other. `example` under another top-level
  domain is not reserved everywhere, so it is not one.
